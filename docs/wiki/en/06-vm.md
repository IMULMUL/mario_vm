# Chapter 6 · The VM Execution Engine

The bytecode produced by the compiler is executed instruction by instruction by the virtual machine (VM). This chapter covers the three cores of the execution engine: **the main loop, the instruction dispatch table, and the two stacks**. The implementation is concentrated in [`mario/mario.c`](../../../mario/mario.c).

## 6.1 The VM instance: vm_t

A `vm_t` is a complete virtual machine (`mario.h`):

```c
typedef struct st_vm {
    bytecode_t   bc;                          // the bytecode being executed
    compiler_func_t compiler;                 // language compiler function pointer

    scope_t*     scope_stack[VM_SCOPE_STACK_MAX];  // scope stack (max 32)
    int32_t      scope_stack_top;
    void*        stack[VM_STACK_MAX];         // operand stack (max 32)
    int32_t      stack_top;
    PC           pc;                          // program counter: index of the next instruction

    bool         terminated;                  // whether it has been terminated
    var_t*       root;                        // global root object (all globals hang under it)

    struct { var_t** cache; ... } var_cache;      // constant cache (runtime optimization)
    struct { load_ncache_t* cache; ... } load_ncache;  // member-access cache

    struct { var_t* var_Object, *var_String, ... } builtin_vars;  // built-in classes/constants
    struct { ...gc fields... } gc;
    var_t*       free_var_buffer;             // free var buffer pool
} vm_t;
```

Creation and initialization:

```c
vm_t* vm = vm_new(js_compile, VAR_CACHE_MAX_DEF, LOAD_NCACHE_MAX_DEF);
vm_init(vm, reg_all_natives, NULL);   // register all built-in classes in on_init
```

`pc` (program counter) is the "pointer" of execution, pointing at an index in `bc.code_buf`.

## 6.2 The main loop: vm_run

This is the heart of the whole VM, and it's surprisingly short:

```c
bool vm_run(vm_t* vm) {
    if(!instr_table_initialized) init_instr_table();   // initialize the dispatch table on first run

    register PC  code_size = vm->bc.cindex;
    register PC* code      = vm->bc.code_buf;

    do {
        // Opportunistic GC safe point: between instructions the value stack and scope
        // stack hold every live var, so collecting here cannot sweep a var a C frame
        // still references bare.
        if(vm->gc.gc_pending && vm->gc.gc_defer == 0 && !vm->gc.is_doing_gc) {
            vm->gc.gc_pending = false;
            gc(vm, false);
        }

        register PC ins          = code[vm->pc++];   // fetch, pc increments
        register opr_code_t instr = OP(ins);          // decode the opcode
        register uint32_t offset  = OFF(ins);         // decode the operand

        if(instr == INSTR_END) break;                 // stop on END

        instr_table[instr](vm, ins, instr, offset);   // dispatch to the handler

        // Service cadence hook: one increment+compare per dispatch when armed
        // (nothing when step_interval is 0); the hook may set vm->terminated to abort.
        if(vm->step_interval != 0 && ++vm->step_count >= vm->step_interval) {
            vm->step_count = 0;
            if(vm->on_step != NULL) vm->on_step(vm, vm->on_step_data);
        }

        if(instr == INSTR_RETURN || instr == INSTR_RETURNV)
            return true;                              // function return: exit this vm_run

        // A yield suspended the generator body this vm_run frame is running:
        // hand control back to gen_resume(), leaving the stacks as they are.
        if(vm->yielded && (instr == INSTR_YIELD || instr == INSTR_YIELD_STAR))
            return false;
    }
    while(vm->pc < code_size && !vm->terminated);
    return false;
}
```

Several key points:

1. **Fetch-decode-execute**: the classic three CPU steps. `code[vm->pc++]` fetches the 32-bit instruction; `OP()`/`OFF()` split out the opcode and operand.
2. **Table-driven dispatch**: `instr_table[instr](...)` uses the opcode as an index to directly call the corresponding handler function pointer. This is faster than a giant `switch` (no branch-prediction pressure) and easier to extend.
3. **GC safe point between instructions**: the top of the loop checks `gc_pending` and only collects between two instructions (when the value/scope stacks fully hold all live objects), avoiding the risk of sweeping a bare reference held by a native C function's stack frame (see Chapter 8).
4. **step service hook**: `step_interval`/`on_step` provide a "call back once every N instructions" mechanism, usable for cooperative scheduling / timeout interruption.
5. **Three ways to exit**:
   - On `INSTR_END`: the whole code finished, return `false`.
   - On `INSTR_RETURN`/`INSTR_RETURNV`: a function returns, return `true`.
   - On `INSTR_YIELD`/`INSTR_YIELD_STAR` with `vm->yielded`: the generator suspends, return `false` (state preserved).

### Why vm_run is called recursively

Note the `return true` in point 5: **function calls are implemented by recursively calling `vm_run`**. Look at `func_call` (`mario.c`):

```c
// script function (not native)
scope_t* sc = scope_new(env);
sc->pc = vm->pc;          // remember the return address at the call site
sc->is_func = true;
vm_push_scope(vm, sc);
vm->pc = func->pc;        // jump to the function body entry
if(vm_run(vm)) {          // recursively execute the body until RETURN
    ret = vm_pop2(vm);    // take the return value
}
```

When execution reaches the body's `RETURN`, the inner `vm_run` returns `true`, control goes back to `func_call`, which restores `pc` to just after the call site and pushes the return value. This is a very concise function-call implementation — it borrows C's own call stack.

## 6.3 The instruction dispatch table

`init_instr_table()` maps each opcode to a handler on first run:

```c
static instr_handler_t instr_table[INSTR_MAX];

static void init_instr_table(void) {
    for(int i=0; i<INSTR_MAX; i++) instr_table[i] = handle_nil;  // default no-op

    instr_table[INSTR_LOAD]  = handle_load;
    instr_table[INSTR_PLUS]  = handle_math;
    instr_table[INSTR_CALL]  = handle_call;
    instr_table[INSTR_CALLO] = handle_call;
    ...
}
```

The handler prototype is uniform:

```c
typedef void (*instr_handler_t)(vm_t* vm, PC ins, opr_code_t instr, uint32_t offset);
```

Multiple opcodes can share one handler. For example, all binary arithmetic (`+ - * / % << >>` and compound assignment) goes through `handle_math`, distinguished by the `instr` parameter; all comparisons go through `handle_compare`.

## 6.4 The operand stack

The operand stack `vm->stack[]` holds values during computation. It has a clever design: **a stack element may be either a `var_t*` (a value) or a `node_t*` (an object member / variable slot)**, distinguished by the `magic` field in the structure's first byte (`var_t.magic==0`, `node_t.magic==1`).

### Push

```c
inline void vm_push(vm_t* vm, var_t* var) {
    var_ref(var);                              // refcount +1, prevent GC from collecting
    vm->stack[vm->stack_top++] = var;
}
inline void vm_push_node(vm_t* vm, node_t* node) {
    var_ref(node->var);
    vm->stack[vm->stack_top++] = node;
}
```

On push, a `var_ref` is done on the inner `var` to ensure it isn't collected by the GC while on the stack.

### Pop

| Function | Behavior |
| --- | --- |
| `vm_pop2(vm)` | pop the top, return its `var_t*` (or `node->var` if it's a node), **without decrementing the refcount**, for handler use |
| `vm_pop(vm)` | pop the top and `var_unref` (truly discard, used by the `POP` instruction) |
| `vm_pop2node(vm)` | pop the top; if it's a node return the `node_t*` (used by assignment statements to get the lvalue target) |
| `vm_stack_pick(vm, depth)` | "pick out" the depth-th element from the stack (extract obj for `obj.method()`) |

`handle_math` is a typical binary-operation handler:

```c
static inline void handle_math(vm_t* vm, PC ins, opr_code_t instr, uint32_t offset) {
    var_t* v2 = vm_pop2(vm);      // right operand
    var_t* v1 = vm_pop2(vm);      // left operand
    math_op(vm, instr, v1, v2);   // compute and push the result
    var_unref(v1);
    var_unref(v2);
}
```

## 6.5 The scope stack

The scope stack `vm->scope_stack[]` manages "where a name is visible". Each layer is a `scope_t`:

```c
typedef struct st_scope {
    var_t*  var;         // this scope's variable container (locals hang under it)
    var_t*  class_var;   // class-definition scope: the constructor var (pushed by CLASS_END so class expressions evaluate to the class)
    PC      pc_start;    // continue anchor for a loop
    PC      pc;          // try's catch anchor / loop's break anchor / function's return address
    int32_t stack_top;   // value-stack height at scope entry (a runtime throw truncates leaked operands accordingly)
    uint32_t is_func:8;  // is a function scope?
    uint32_t is_block:8; // is an ordinary code block?
    uint32_t is_try:8;   // is a try block?
    uint32_t is_loop:4;  // is a loop?
    uint32_t is_switch:4;// is a switch scope? (break stops here, continue does not)
    uint32_t is_strict:4;// strict mode?
    func_t*  func;       // if a function scope, points to the func_t (with closure info)
    var_t*   func_var;   // the function OBJECT var owning func_t (a back-pointer keeping it reachable during the body, so GC won't sweep it)
    struct st_scope* prev;  // points to the outer scope, forming a chain
} scope_t;
```

Different kinds of scope are created uniformly by `handle_block` (`BLOCK`/`LOOP`/`TRY` share it), differing only in the flags and anchors set:

```c
static inline void handle_block(vm_t* vm, PC ins, opr_code_t instr, uint32_t offset) {
    scope_t* sc = scope_new(var_new_block(vm));
    sc->is_block = true;
    if(instr == INSTR_LOOP) {
        sc->is_loop = true;
        sc->pc_start = vm->pc+1;   // continue anchor
        sc->pc       = vm->pc+2;   // break anchor
    } else if(instr == INSTR_TRY) {
        sc->is_try = true;
        sc->pc = vm->pc+1;         // catch anchor
    }
    vm_push_scope(vm, sc);
}
```

`BLOCK_END`/`LOOP_END`/`TRY_END` all call `handle_block_end` → `vm_pop_scope`, popping and releasing that scope layer (also triggering a GC check).

### Variable lookup: vm_find_in_scopes

When looking up a name, it walks outward along the `prev` chain from the current scope:

```c

    //    - look in the scope's `this` object (member methods can access fields directly)

```

This is the implementation of the JS scope chain. Step ①'s closure-chain lookup is the key to closures "remembering" their defining environment (details in Chapter 7).

### How break / continue work

They don't rely on jump offsets in the bytecode; instead they **inspect the scope stack at runtime**:

```c
static inline void handle_break(vm_t* vm, ...) {
    while(true) {
        scope_t* sc = vm_get_scope(vm);
        if(sc == NULL) { /* error: not inside a loop */ vm_terminate(vm); break; }
        if(sc->is_loop) { vm->pc = sc->pc; break; }  // jump to the break anchor
        vm_pop_scope(vm);                             // pop the inner scope, keep looking
    }
}
```

`handle_continue` is similar, except it jumps to `sc->pc_start` (the continue anchor). This design lets break/continue correctly penetrate nested code blocks to find the nearest loop.

## 6.6 The full function-call flow: handle_call

`INSTR_CALL` (ordinary call) and `INSTR_CALLO` (member-method call) share `handle_call`:

```c
static inline void handle_call(vm_t* vm, ...) {
    const char* s = bc_getstr(&vm->bc, offset);   // e.g. "log$1"
    int arg_num = parse_func_name(s, name);       // parse out the name "log" and arg count 1

    if(instr == INSTR_CALLO)
        obj = vm_stack_pick(vm, arg_num+1);       // pick obj (this) out of the stack
    else {
        obj = vm_this_in_scopes(vm);
        func = find_func(vm, sc_var, name);       // first look for the function in the current scope
    }
    if(func == NULL && obj != NULL)
        func = find_func(vm, obj, name);          // then look on the object / prototype chain

    // if what's found is a class rather than a function → find its constructor
    ...
    if(func != NULL) func_call(vm, obj, func, arg_num);
    else { /* clear the stack, push undefined, report an error */ }
}
```

Calling convention: **arguments are already pushed in order before the call** (guaranteed by the compiler); the stack layout is `[obj(CALLO only), arg1, arg2, ...]`. `func_call` will:

1. create the function environment `env` (a new object), putting the `arguments` array and `this` into it;
2. pop `arg_num` actual arguments off the stack and bind them to `env` by parameter name;
3. if it's a **native function**: directly call the C function pointer `func->native(vm, env, data)`;
4. if it's a **script function**: create a new function scope, `vm->pc = func->pc`, recursively `vm_run`;
5. push the return value.

## 6.7 Return-value handling: handle_return

```c
static inline void handle_return(vm_t* vm, ...) {
    if(instr == INSTR_RETURN)
        vm_push(vm, var_new(vm));      // no return value → push undefined
    else
        ret = vm_pop2(vm), vm_push(vm, ret);  // has a return value → normalize to the top

    // unwind the scope stack, popping all non-function scopes until a function scope is found
    while(true) {
        scope_t* sc = vm_get_scope(vm);
        if(sc->is_func) {
            func_set_closure(ret, sc->var, sc->func);  // if returning a function, set up its closure
            vm->pc = sc->pc;      // restore the return address
            vm_pop_scope(vm);
            break;
        }
        vm_pop_scope(vm);         // pop inner block/loop scopes still present at return time
    }
}
```

Back in `vm_run`, because `instr==INSTR_RETURN`, the main loop does `return true`, handing control back to the `func_call` one level up.

## 6.8 Runtime optimization: inline caches

Mario has two "optimize while running" mechanisms, implemented by modifying instructions in `code_buf` (this is what the instruction OPTION bit `INSTR_OPT_CACHE` is for):

- **Variable/constant cache `var_cache`**: `handle_int`/`handle_str` etc., after first creating a constant, cache the result; if they find the next instruction is `POP` (meaning the result isn't used), they change the instruction to `INSTR_NIL` and mark the previous one as cached, avoiding repeated object creation.
- **Member-access cache `load_ncache`**: when `handle_load` accesses a member inside a loop scope, it remembers the resolved `node_t`; next time it loads it quickly via `INSTR_NCACHE`, skipping the scope-chain lookup.

Beginners can skip these optimizations at first, but they embody the interesting design that "bytecode is not read-only — it can rewrite itself at runtime".

## 6.9 Summary

- `vm_run` is the fetch-decode-dispatch main loop, dispatching via the function-pointer table `instr_table`.
- Function calls are implemented via **recursive `vm_run`**; the return address is stored in the function scope's `sc->pc`.
- The **operand stack** holds values/nodes, distinguished by `magic`; the **scope stack** manages name visibility and control-flow anchors.
- `break`/`continue`/`return`/`throw` all locate their target by traversing the scope stack at runtime, rather than via hard-coded jumps.
