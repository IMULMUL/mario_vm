# Chapter 8 · Memory Management and Garbage Collection

Scripting languages don't require the programmer to `free` manually; this "automatic memory management" is the VM's job. Mario uses a **hybrid strategy that is very practical in embedded scenarios: reference counting as the primary mechanism + mark-and-sweep as a backstop + an object buffer pool for reuse**.

## 8.1 The lowest level: platform memory functions

Mario doesn't call `malloc`/`free` directly, but through function pointers (`mario.h`):

```c
extern void* (*_platform_malloc)(uint32_t size);
extern void  (*_platform_free)(void* p);

void* mario_malloc(uint32_t size);   // wraps _platform_malloc
void  mario_free(void* p);           // wraps _platform_free
void* mario_realloc(void* p, uint32_t old_size, uint32_t new_size);
```

The benefit: when porting to an embedded platform without a standard library, you only need to point these three pointers at your own allocator. When `MARIO_DEBUG` is on, they point at the versions in `mem_debug.c` with statistics and bounds checking.

## 8.2 Three basic containers

The kernel ships three lightweight containers, all free of third-party dependencies:

### m_array_t — dynamic array
```c
typedef struct st_array {
    void**   items;
    uint32_t max: 16;   // capacity
    uint32_t size: 16;  // current element count
} m_array_t;
```
Used for the string table, function-argument tables, closure chains, etc. `array_add` grows by a multiple when full.

### mstr_t — mutable string
```c
typedef struct st_mstr {
    char*    cstr;
    uint32_t max: 16;   // buffer capacity
    uint32_t len: 16;   // current length
} mstr_t;
```
The lexer concatenates tokens with it, and string operations and JSON serialization rely on it. Note that functions like `mstr_from_int` return their result in a static buffer `_mstr_result[STATIC_mstr_MAX+1]` (32 bytes) — "use-and-discard" convenience functions.

### hash_map_t — hash table
```c
typedef struct st_hash_map {
    hash_entry_t** buckets;
    uint32_t size, capacity;
    uint32_t load_factor_num, load_factor_den;  // load factor
} hash_map_t;
```
Every `var_t`'s `children` is a hash table, using chaining to resolve collisions and growing past the load factor. This guarantees O(1) object-member lookup.

## 8.3 The var_t lifecycle

A `var_t` flows between several linked lists from creation to collection. It has a `status` field (`V_ST_FREE`/`V_ST_GC_FREE`/`V_ST_GC`/`V_ST_REF`) and a `refs` reference count.

```
       var_new()
          │  status = V_ST_REF, refs = 0
          ▼
   ┌─────────────┐   var_ref()    ┌──────────────┐
   │  in use      │◄──────────────│  refs > 0     │
   │ (V_ST_REF)  │───────────────►│  referenced    │
   └─────────────┘   var_unref()   └──────────────┘
          │ refs hits 0
          ▼
      var_free()  ──► added to the "free buffer pool" free_var_buffer
          ▲
          │ GC deems it unreachable
   ┌──────────────┐
   │  GC watch list │  gc_vars (status = V_ST_GC)
   └──────────────┘
```

### var_ref / var_unref: reference counting

```c
inline var_t* var_ref(var_t* var) {
    ++var->refs;
    if(var->status == V_ST_GC) {      // if it's on the GC watch list
        remove_from_gc(var);          // take it off
        var->status = V_ST_REF;       // restore to "referenced"
    }
    return var;
}

inline void var_unref(var_t* var) {
    if(var->refs > 0) --var->refs;
    if(var->refs == 0)
        var_free(var);                // nobody references it → free immediately
    else if(var->status == V_ST_REF)
        add_to_gc(var);               // still referenced → put on the GC watch list
}
```

This is the core rhythm of Mario's memory management:

- `var_ref` when **pushing onto the stack, binding to a scope, adding to an object**;
- `var_unref` when **popping off the stack, leaving a scope, done using it**;
- reference count hits zero → collect immediately, no need to wait for the GC.

Recall `vm_push`/`vm_pop` from Chapter 6: push does `var_ref`, pop does `var_unref` — exactly this mechanism.

### var_free: not a real free

`var_free` doesn't immediately return memory to the system; it clears the contents and puts it into the **free buffer pool** for reuse:

```c
void var_free(void* p) {
    var_t* var = (var_t*)p;
    uint32_t status = var->status;
    // if it's a function, release closure references first
    var_clean(var);            // clear children, value, etc.
    var->type = V_UNDEF;
    if(status == V_ST_GC) {
        if(vm->gc.is_doing_gc) var->status = V_ST_GC_FREE;  // during GC, defer processing
        else { remove_from_gc(var); add_to_free(var); }
    } else if(status != V_ST_FREE) {
        add_to_free(var);      // put into the free pool
    }
}
```

`var_new` prefers to take from the free pool:

```c
inline var_t* var_new(vm_t* vm) {
    var_t* var = get_from_free(vm);       // reuse a free one first
    if(var == NULL) var = mario_malloc(sizeof(var_t));  // allocate only if none
    memset(var, 0, sizeof(var_t));
    var->type = V_UNDEF;
    var->status = V_ST_REF;
    hash_map_init(&var->children);
    return var;
}
```

**Why a buffer pool matters**: script execution frequently creates/destroys temporary values (every operation produces an intermediate result). Reusing already-allocated `var_t` memory blocks significantly reduces `malloc`/`free` calls and fragmentation — especially important for embedded systems. The pool size is controlled by `free_var_buffer_num` (default `FREE_VAR_BUFFER_NUM_DEF = 128`).

## 8.4 Why mark-and-sweep is still needed

Reference counting has a fatal weakness: **it cannot collect circular references**. For example:

```javascript
var a = {};
var b = {};
a.ref = b;
b.ref = a;
a = null;
b = null;
```

Now `a` and `b` reference each other, each with a non-zero `refs`, but they are already unreachable (garbage). This is where the mark-and-sweep GC comes in.

### Trigger timing (opportunistic, deferred to a safe point)

When the GC watch list `gc_vars` exceeds the threshold, it does **not** collect on the spot; instead it sets a `gc_pending` flag, deferring execution to the next safe point:

```c
static inline void add_to_gc(var_t* var) {
    vm_t* vm = var->vm;
    if(vm == NULL) return;              // sentinel: recycled heap, not a live variable — return
    // ... O(1) append to the gc_vars list via the tail pointer gc_vars_tail ...
    var->status = V_ST_GC;
    vm->gc.gc_vars_num++;

    /* Do not trigger a gc while an object graph is being torn down (var_clean):
     * the re-entrant gc_free_free_vars() would mario_free() vars that pending
     * node_free() calls in the same teardown still dereference, causing a
     * use-after-free. So defer it to the next opportunity outside a teardown. */
    if(vm->gc.gc_vars_num > vm->gc.gc_trig_var_num && vm->gc.gc_defer == 0)
        vm->gc.gc_pending = true; /* consumed at the next vm_run safe point */
}
```

This `gc_pending` flag is consumed at the top of the `vm_run` main loop described in Chapter 6: only **between two instructions** (when the value/scope stacks fully hold all live variables and no native C frame references a var bare) does it actually call `gc(vm, false)`. This is the "opportunistic GC safe point".

Two safety-related fields:

- **`gc_defer`**: >0 while the object graph is temporarily unrooted (`var_clean` teardown, `func_call` argument setup); opportunistic GC is deferred then to avoid mis-sweeping.
- **`gc_pending`**: a GC that was requested but deferred to the next `vm_run` instruction boundary.

In addition, `vm_pop_scope` (scope pop) also does a `gc(vm, false)` check.

### The mark-and-sweep algorithm: gc_vars

```c
static inline void gc_vars(vm_t* vm) {
    // ① starting from the "roots", mark all reachable objects
    gc_mark(vm->root, true);        // the global object and its members
    gc_mark_stack(vm, true);        // objects on the operand stack
    gc_mark_cache(vm, true);        // objects in the caches

    // ② free the "unmarked" objects on the watch list (unreachable = garbage)
    var_t* v = vm->gc.gc_vars;
    while(v != NULL) {
        var_t* next = v->next;
        if(v->status == V_ST_GC && v->gc_marked == false)
            var_free(v);
        v = next;
    }

    // ③ clear the marks, ready for the next GC
    gc_mark(vm->root, false);
    gc_mark_stack(vm, false);
    gc_mark_cache(vm, false);

    // ④ move objects marked GC_FREE during the GC into the free pool for reuse
    ...
}
```

Three "roots":
1. **`vm->root`**: the global object; all global variables/built-in classes are reachable;
2. **operand stack**: intermediate values being computed;
3. **caches**: constants cached by runtime optimization in `var_cache`.

### Marking recursion and cycle guarding

`gc_mark` recursively traverses an object's `children`:

```c
static inline void gc_mark(var_t* var, bool mark) {
    if(var_empty(var)) return;
    var->gc_marking = true;       // mark "in progress", preventing infinite recursion on cycles
    var->gc_marked = mark;
    hash_map_iterate(&var->children, gc_mark_callback, &mark);  // recursively mark all members
    var->gc_marking = false;
}
```

The `gc_marking` field is the key to cycle guarding: if an object is being marked, encountering it again skips it, avoiding infinite `a→b→a` recursion.

## 8.5 The gc controller

```c
static inline void gc(vm_t* vm, bool force) {
    if(vm->gc.is_doing_gc) return;                        // re-entrancy guard
    if(!force && vm->gc.gc_defer > 0) return;             // a C frame holds bare var pointers, defer
    if(!force && vm->gc.gc_vars_num < vm->gc.gc_trig_var_num)
        return;                                            // below threshold, skip
    vm->gc.is_doing_gc = true;
    gc_vars(vm);                                           // mark-and-sweep
    gc_free_free_vars(vm, force ? 0 : vm->gc.free_var_buffer_num);  // shrink the free pool
    vm->gc.is_doing_gc = false;

    /* Adaptive trigger: gc_vars_num is now the surviving live count. Require the
     * heap to grow ~1.5x past it before the next opportunistic collection, so
     * building a large all-live structure (a big array/object literal) costs
     * amortized O(n) instead of re-marking the whole heap on every allocation
     * past a fixed floor - the O(n^2) that froze the engine for seconds. */
    uint32_t live = vm->gc.gc_vars_num;
    uint32_t trig = live + (live >> 1);
    vm->gc.gc_trig_var_num = (trig < GC_TRIG_VAR_NUM_DEF) ? GC_TRIG_VAR_NUM_DEF : trig;
}
```

- `force=false`: ordinary opportunistic collection, only when the watch list is large enough; the free pool keeps a certain count for reuse.
- `force=true`: thorough collection (e.g. on VM shutdown); the free pool is emptied and all memory returned to the system.

**The adaptive threshold is the key to the "gc speed up"**: earlier versions used a fixed threshold (`GC_TRIG_VAR_NUM_DEF = 128`). When a script built a very large, all-live object (say a big object with thousands of members), every newly added variable triggered a full-heap re-mark, degenerating overall to O(n²) and freezing the engine for seconds. Now, after a collection the next trigger threshold is raised to "live count × 1.5" (never below the fixed floor of 128), making large-heap construction amortized O(n); and a collection that frees a lot shrinks the threshold back, so small heaps still collect promptly.

`gc_free_free_vars` truly `mario_free`s the surplus free blocks when the free pool exceeds the retained amount.

## 8.6 Why the hybrid strategy suits embedded systems

| Mechanism | Advantage | Role in this project |
| --- | --- | --- |
| Reference counting | Prompt collection, no pause peaks | The vast majority of temporaries are collected on unref |
| Mark-and-sweep | Handles circular references | Backstop cleaning of refcounting's blind spot |
| Free buffer pool | Fewer malloc/free, less fragmentation | Frequently created temporary `var_t`s reuse the same memory |
| Opportunistic safe point | Collection happens only when all live vars are rooted | Avoids mis-sweeping bare references in native C frames |
| Adaptive threshold | GC neither too frequent nor degenerate to O(n²) | Trigger threshold moves up dynamically with live×1.5 (never below 128) |

This combination lets Mario run scripts stably even on microcontrollers with no large memory and no OS memory-management support.

## 8.7 Summary

- Memory allocation is abstracted as `_platform_malloc/free`, easy to port.
- `var_t` is managed by reference counting; when `refs` hits zero it's collected.
- Collection is not a real `free`; it clears then goes into the **free pool** for reuse.
- Circular references are backstopped by **mark-and-sweep GC**: mark reachable objects from the three roots root/stack/cache, sweep the unreachable.
- GC is **opportunistic**: `add_to_gc` only sets `gc_pending`; the real collection is deferred to a safe point at a `vm_run` instruction boundary.
- The **adaptive trigger threshold** (live count × 1.5) reduces large-heap construction from O(n²) to amortized O(n) — the core of the "gc speed up".
- `gc_marking` prevents infinite recursion during the mark phase.
