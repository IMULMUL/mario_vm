# 第 6 章 · 虚拟机执行引擎

编译器产出的字节码，由虚拟机（VM）逐条执行。本章讲解执行引擎的三个核心：**主循环、指令分发表、两个栈**。实现集中在 [`mario/mario.c`](../../../mario/mario.c)。

## 6.1 虚拟机实例：vm_t

一个 `vm_t` 就是一台完整的虚拟机（`mario.h`）：

```c
typedef struct st_vm {
    bytecode_t   bc;                          // 正在执行的字节码
    compiler_func_t compiler;                 // 语言编译器函数指针

    scope_t*     scope_stack[VM_SCOPE_STACK_MAX];  // 作用域栈（最大 32）
    int32_t      scope_stack_top;
    void*        stack[VM_STACK_MAX];         // 操作数栈（最大 32）
    int32_t      stack_top;
    PC           pc;                          // 程序计数器：下一条要执行的指令下标

    bool         terminated;                  // 是否被终止
    var_t*       root;                        // 全局根对象（所有全局变量挂在它下面）

    struct { var_t** cache; ... } var_cache;      // 常量缓存（运行时优化）
    struct { load_ncache_t* cache; ... } load_ncache;  // 成员访问缓存

    struct { var_t* var_Object, *var_String, ... } builtin_vars;  // 内建类/常量
    struct { ...gc 相关字段... } gc;
    var_t*       free_var_buffer;             // 空闲 var 缓冲池
} vm_t;
```

创建与初始化：

```c
vm_t* vm = vm_new(js_compile, VAR_CACHE_MAX_DEF, LOAD_NCACHE_MAX_DEF);
vm_init(vm, reg_all_natives, NULL);   // on_init 里注册所有内建类
```

`pc`（program counter）是执行的「指针」，指向 `bc.code_buf` 里的下标。

## 6.2 主循环：vm_run

这是整个 VM 的心脏，出奇地短：

```c
bool vm_run(vm_t* vm) {
    if(!instr_table_initialized) init_instr_table();   // 首次运行初始化分发表

    register PC  code_size = vm->bc.cindex;
    register PC* code      = vm->bc.code_buf;

    do {
        // 机会式 GC 安全点：指令之间值栈/作用域栈持有所有活变量，
        // 在此回收不会误扫某个 C 栈帧仍裸引用的 var。
        if(vm->gc.gc_pending && vm->gc.gc_defer == 0 && !vm->gc.is_doing_gc) {
            vm->gc.gc_pending = false;
            gc(vm, false);
        }

        register PC ins          = code[vm->pc++];   // 取指，pc 自增
        register opr_code_t instr = OP(ins);          // 解码操作码
        register uint32_t offset  = OFF(ins);         // 解码操作数

        if(instr == INSTR_END) break;                 // 遇到 END 结束

        instr_table[instr](vm, ins, instr, offset);   // 分发给 handler 执行

        // 服务节奏钩子：武装后每次分发做一次自增+比较（step_interval 为 0 时什么都不做），
        // 钩子可置 vm->terminated 中止整个嵌套运行。
        if(vm->step_interval != 0 && ++vm->step_count >= vm->step_interval) {
            vm->step_count = 0;
            if(vm->on_step != NULL) vm->on_step(vm, vm->on_step_data);
        }

        if(instr == INSTR_RETURN || instr == INSTR_RETURNV)
            return true;                              // 函数返回：退出本次 vm_run

        // yield 挂起了本 vm_run 帧正在跑的生成器体：把控制权交回 gen_resume()，保留栈现场。
        if(vm->yielded && (instr == INSTR_YIELD || instr == INSTR_YIELD_STAR))
            return false;
    }
    while(vm->pc < code_size && !vm->terminated);
    return false;
}
```

几个关键点：

1. **取指-解码-执行**：经典的 CPU 三步。`code[vm->pc++]` 取出 32 位指令，`OP()`/`OFF()` 拆出操作码和操作数。
2. **表驱动分发**：`instr_table[instr](...)` 用操作码作下标，直接调用对应的 handler 函数指针。这比一个巨大的 `switch` 更快（无分支预测压力），也更易扩展。
3. **指令间的 GC 安全点**：循环顶部检查 `gc_pending`，在两条指令之间（此时值栈/作用域栈完整持有所有活对象）才做回收，避开 native C 函数栈帧裸引用被误扫的风险（详见第 8 章）。
4. **step 服务钩子**：`step_interval`/`on_step` 提供一个「每执行若干条指令回调一次」的机制，可用于协作式调度/超时中断。
5. **三种退出方式**：
   - 遇到 `INSTR_END`：整段代码执行完，返回 `false`。
   - 遇到 `INSTR_RETURN`/`INSTR_RETURNV`：函数返回，返回 `true`。
   - 遇到 `INSTR_YIELD`/`INSTR_YIELD_STAR` 且 `vm->yielded`：生成器挂起，返回 `false`（保留现场）。

### 为什么 vm_run 会被递归调用

注意第 2 点里的 `return true`：**函数调用是通过递归调用 `vm_run` 实现的**。看 `func_call`（`mario.c`）：

```c
// 脚本函数（非 native）
scope_t* sc = scope_new(env);
sc->pc = vm->pc;          // 记住调用点的返回地址
sc->is_func = true;
vm_push_scope(vm, sc);
vm->pc = func->pc;        // 跳到函数体入口
if(vm_run(vm)) {          // 递归执行函数体，直到遇到 RETURN
    ret = vm_pop2(vm);    // 取返回值
}
```

执行到函数体的 `RETURN` 时，内层 `vm_run` 返回 `true`，控制权回到 `func_call`，它恢复 `pc` 到调用点之后，把返回值压栈。这是一种非常简洁的函数调用实现——直接借用 C 的调用栈。

## 6.3 指令分发表

`init_instr_table()` 在首次运行时把每个操作码映射到 handler：

```c
static instr_handler_t instr_table[INSTR_MAX];

static void init_instr_table(void) {
    for(int i=0; i<INSTR_MAX; i++) instr_table[i] = handle_nil;  // 默认空操作

    instr_table[INSTR_LOAD]  = handle_load;
    instr_table[INSTR_PLUS]  = handle_math;
    instr_table[INSTR_CALL]  = handle_call;
    instr_table[INSTR_CALLO] = handle_call;
    ...
}
```

handler 的函数原型统一为：

```c
typedef void (*instr_handler_t)(vm_t* vm, PC ins, opr_code_t instr, uint32_t offset);
```

多个操作码可以共用一个 handler。例如所有二元算术运算（`+ - * / % << >>` 及复合赋值）都走 `handle_math`，靠 `instr` 参数区分具体运算；所有比较运算走 `handle_compare`。

## 6.4 操作数栈

操作数栈 `vm->stack[]` 存放计算过程中的值。它有个巧妙设计：**栈元素既可能是 `var_t*`（值），也可能是 `node_t*`（对象成员/变量槽）**，两者用结构体首字节的 `magic` 字段区分（`var_t.magic==0`，`node_t.magic==1`）。

### 压栈

```c
inline void vm_push(vm_t* vm, var_t* var) {
    var_ref(var);                              // 引用计数 +1，防 GC 回收
    vm->stack[vm->stack_top++] = var;
}
inline void vm_push_node(vm_t* vm, node_t* node) {
    var_ref(node->var);
    vm->stack[vm->stack_top++] = node;
}
```

压栈时对内部的 `var` 做一次 `var_ref`，保证它在栈上期间不会被 GC 回收。

### 弹栈

| 函数 | 行为 |
| --- | --- |
| `vm_pop2(vm)` | 弹出栈顶，返回其 `var_t*`（若是 node 则返回 `node->var`），**不减引用**，供 handler 使用 |
| `vm_pop(vm)` | 弹出栈顶并 `var_unref`（真正丢弃，用于 `POP` 指令） |
| `vm_pop2node(vm)` | 弹出栈顶，若它是 node 则返回 `node_t*`（赋值语句取左值目标用） |
| `vm_stack_pick(vm, depth)` | 从栈中「抽出」第 depth 个元素（`obj.method()` 时取出 obj） |

`handle_math` 是典型的二元运算 handler：

```c
static inline void handle_math(vm_t* vm, PC ins, opr_code_t instr, uint32_t offset) {
    var_t* v2 = vm_pop2(vm);      // 右操作数
    var_t* v1 = vm_pop2(vm);      // 左操作数
    math_op(vm, instr, v1, v2);   // 计算并压入结果
    var_unref(v1);
    var_unref(v2);
}
```

## 6.5 作用域栈

作用域栈 `vm->scope_stack[]` 管理「名字在哪里可见」。每一层是一个 `scope_t`：

```c
typedef struct st_scope {
    var_t*  var;         // 本作用域的变量容器（局部变量都挂在它下面）
    var_t*  class_var;   // 类定义作用域：构造器 var（CLASS_END 压入，使类表达式求值为该类）
    PC      pc_start;    // 循环的 continue 锚点
    PC      pc;          // try 的 catch 锚点 / 循环的 break 锚点 / 函数的返回地址
    int32_t stack_top;   // 进入作用域时的值栈高度（运行时 throw 据此截断泄漏的操作数）
    uint32_t is_func:8;  // 是函数作用域？
    uint32_t is_block:8; // 是普通代码块？
    uint32_t is_try:8;   // 是 try 块？
    uint32_t is_loop:4;  // 是循环？
    uint32_t is_switch:4;// 是 switch 作用域？（break 在此停，continue 不会）
    uint32_t is_strict:4;// 严格模式？
    func_t*  func;       // 若是函数作用域，指向 func_t（含闭包信息）
    var_t*   func_var;   // 拥有 func_t 的函数对象 var（回指针，保证它在函数体执行期间可达，不被 GC 误扫）
    struct st_scope* prev;  // 指向外层作用域，形成链
} scope_t;
```

不同类型的作用域由 `handle_block` 统一创建（`BLOCK`/`LOOP`/`TRY` 共用），只是设置的标志位和锚点不同：

```c
static inline void handle_block(vm_t* vm, PC ins, opr_code_t instr, uint32_t offset) {
    scope_t* sc = scope_new(var_new_block(vm));
    sc->is_block = true;
    if(instr == INSTR_LOOP) {
        sc->is_loop = true;
        sc->pc_start = vm->pc+1;   // continue 锚点
        sc->pc       = vm->pc+2;   // break 锚点
    } else if(instr == INSTR_TRY) {
        sc->is_try = true;
        sc->pc = vm->pc+1;         // catch 锚点
    }
    vm_push_scope(vm, sc);
}
```

`BLOCK_END`/`LOOP_END`/`TRY_END` 都调用 `handle_block_end` → `vm_pop_scope`，弹出并释放这层作用域（同时触发一次 GC 检查）。

### 变量查找：vm_find_in_scopes

查找一个名字时，从当前作用域沿 `prev` 链向外层回溯：

```c
static inline node_t* vm_find_in_scopes(vm_t* vm, const char* name) {
    // ① 若在函数作用域，先沿闭包链查找（支持闭包捕获外层变量）
    // ② 从当前作用域向外层遍历：
    //    - 在 scope->var 里找
    //    - 在 scope 的 this 对象里找（成员方法能直接访问字段）
    // ③ 最后在全局 root 里找
}
```

这就是 JS 作用域链的实现。第 ① 步的闭包链查找是闭包能「记住」定义环境的关键（详见第 7 章）。

### break / continue 如何工作

它们不靠字节码里的跳转偏移，而是**运行时查作用域栈**：

```c
static inline void handle_break(vm_t* vm, ...) {
    while(true) {
        scope_t* sc = vm_get_scope(vm);
        if(sc == NULL) { /* 报错：不在循环里 */ vm_terminate(vm); break; }
        if(sc->is_loop) { vm->pc = sc->pc; break; }  // 跳到 break 锚点
        vm_pop_scope(vm);                             // 弹出内层作用域，继续找
    }
}
```

`handle_continue` 类似，只是跳到 `sc->pc_start`（continue 锚点）。这种设计让 break/continue 能正确穿透嵌套的代码块，找到最近的循环。

## 6.6 函数调用全流程：handle_call

`INSTR_CALL`（普通调用）和 `INSTR_CALLO`（成员方法调用）共用 `handle_call`：

```c
static inline void handle_call(vm_t* vm, ...) {
    const char* s = bc_getstr(&vm->bc, offset);   // 如 "log$1"
    int arg_num = parse_func_name(s, name);       // 解析出名字 "log" 和参数数 1

    if(instr == INSTR_CALLO)
        obj = vm_stack_pick(vm, arg_num+1);       // 从栈里抽出 obj（this）
    else {
        obj = vm_this_in_scopes(vm);
        func = find_func(vm, sc_var, name);       // 先在当前作用域找函数
    }
    if(func == NULL && obj != NULL)
        func = find_func(vm, obj, name);          // 再在对象/原型链上找

    // 若找到的是类而非函数 → 找它的 constructor
    ...
    if(func != NULL) func_call(vm, obj, func, arg_num);
    else { /* 清栈、压 undefined、抛错 */ }
}
```

调用约定：**参数在调用前已按顺序压栈**（编译器保证），栈布局是 `[obj(仅CALLO), arg1, arg2, ...]`。`func_call` 会：

1. 创建函数环境 `env`（一个新对象），把 `arguments` 数组和 `this` 放进去；
2. 从栈上弹出 `arg_num` 个实参，按形参名绑定到 `env`；
3. 若是 **native 函数**：直接调用 C 函数指针 `func->native(vm, env, data)`；
4. 若是 **脚本函数**：新建函数作用域，`vm->pc = func->pc`，递归 `vm_run`；
5. 把返回值压栈。

## 6.7 返回值处理：handle_return

```c
static inline void handle_return(vm_t* vm, ...) {
    if(instr == INSTR_RETURN)
        vm_push(vm, var_new(vm));      // 无返回值 → 压 undefined
    else
        ret = vm_pop2(vm), vm_push(vm, ret);  // 有返回值 → 规范化到栈顶

    // 沿作用域栈回溯，弹出所有非函数作用域，直到找到函数作用域
    while(true) {
        scope_t* sc = vm_get_scope(vm);
        if(sc->is_func) {
            func_set_closure(ret, sc->var, sc->func);  // 若返回的是函数，设置闭包
            vm->pc = sc->pc;      // 恢复返回地址
            vm_pop_scope(vm);
            break;
        }
        vm_pop_scope(vm);         // 弹出 return 时仍存在的内层块/循环作用域
    }
}
```

回到 `vm_run`，因为 `instr==INSTR_RETURN`，主循环 `return true`，控制权交回上一层的 `func_call`。

## 6.8 运行时优化：内联缓存

Mario 有两处「边跑边优化」的机制，通过修改 `code_buf` 里的指令实现（这就是指令 OPTION 位 `INSTR_OPT_CACHE` 的用途）：

- **变量/常量缓存 `var_cache`**：`handle_int`/`handle_str` 等在第一次创建常量后，把结果缓存起来，若发现下一条是 `POP`（说明结果没被用），就把指令改成 `INSTR_NIL` 并把前一条标记为已缓存，避免重复创建对象。
- **成员访问缓存 `load_ncache`**：`handle_load` 在循环作用域里访问成员时，记住解析到的 `node_t`，下次直接用 `INSTR_NCACHE` 快速加载，省去作用域链查找。

这些优化对初学者可以先略过，但它们体现了「字节码不是只读的，运行时可以自我改写」这一有趣设计。

## 6.9 小结

- `vm_run` 是取指-解码-分发的主循环，用函数指针表 `instr_table` 做分发。
- 函数调用通过**递归 `vm_run`** 实现，返回地址存在函数作用域的 `sc->pc`。
- **操作数栈**存值/节点，用 `magic` 区分；**作用域栈**管理名字可见性与控制流锚点。
- `break`/`continue`/`return`/`throw` 都靠运行时遍历作用域栈定位目标，而非硬编码跳转。
