# 第 8 章 · 内存管理与垃圾回收

脚本语言不需要程序员手动 `free`，这套「自动内存管理」由 VM 负责。Mario 采用了一种在嵌入式场景很实用的**混合策略：引用计数为主 + 标记清除兜底 + 对象缓冲池复用**。

## 8.1 最底层：平台内存函数

Mario 不直接调用 `malloc`/`free`，而是通过函数指针（`mario.h`）：

```c
extern void* (*_platform_malloc)(uint32_t size);
extern void  (*_platform_free)(void* p);

void* mario_malloc(uint32_t size);   // 封装 _platform_malloc
void  mario_free(void* p);           // 封装 _platform_free
void* mario_realloc(void* p, uint32_t old_size, uint32_t new_size);
```

这样做的好处：移植到没有标准库的嵌入式平台时，只需把这三个指针指向你自己的分配器。打开 `MARIO_DEBUG` 时，它们会指向 `mem_debug.c` 里带统计和越界检查的版本。

## 8.2 三个基础容器

内核自带三个轻量容器，全部无第三方依赖：

### m_array_t —— 动态数组
```c
typedef struct st_array {
    void**   items;
    uint32_t max: 16;   // 容量
    uint32_t size: 16;  // 当前元素数
} m_array_t;
```
用于字符串表、函数参数表、闭包链等。`array_add` 在满时按倍数扩容。

### mstr_t —— 可变字符串
```c
typedef struct st_mstr {
    char*    cstr;
    uint32_t max: 16;   // 缓冲区容量
    uint32_t len: 16;   // 当前长度
} mstr_t;
```
词法分析器拼接 token、字符串运算、JSON 序列化都靠它。注意 `mstr_from_int` 等函数用一个静态缓冲区 `_mstr_result[STATIC_mstr_MAX+1]`（32 字节）返回结果，属于「用完即弃」的便捷函数。

### hash_map_t —— 哈希表
```c
typedef struct st_hash_map {
    hash_entry_t** buckets;
    uint32_t size, capacity;
    uint32_t load_factor_num, load_factor_den;  // 负载因子
} hash_map_t;
```
每个 `var_t` 的 `children` 就是一张哈希表，用「拉链法」解决冲突，超过负载因子时扩容。这保证了对象成员查找是 O(1)。

## 8.3 var_t 的生命周期

一个 `var_t` 从创建到回收，会在几条链表之间流转。它有一个 `status` 字段（`V_ST_FREE`/`V_ST_GC_FREE`/`V_ST_GC`/`V_ST_REF`）和一个 `refs` 引用计数。

```
       var_new()
          │  status = V_ST_REF, refs = 0
          ▼
   ┌─────────────┐   var_ref()    ┌──────────────┐
   │  正在使用    │◄──────────────│  refs > 0     │
   │ (V_ST_REF)  │───────────────►│  被引用        │
   └─────────────┘   var_unref()   └──────────────┘
          │ refs 归 0
          ▼
      var_free()  ──► 加入「空闲缓冲池」free_var_buffer
          ▲
          │ GC 判定不可达
   ┌──────────────┐
   │  GC 观察列表  │  gc_vars（status = V_ST_GC）
   └──────────────┘
```

### var_ref / var_unref：引用计数

```c
inline var_t* var_ref(var_t* var) {
    ++var->refs;
    if(var->status == V_ST_GC) {      // 若它在 GC 观察列表里
        remove_from_gc(var);          // 取出来
        var->status = V_ST_REF;       // 恢复为「被引用」
    }
    return var;
}

inline void var_unref(var_t* var) {
    if(var->refs > 0) --var->refs;
    if(var->refs == 0)
        var_free(var);                // 没人引用了 → 立即释放
    else if(var->status == V_ST_REF)
        add_to_gc(var);               // 还有引用 → 放进 GC 观察列表待查
}
```

这是 Mario 内存管理的核心节奏：

- **压栈、绑定到作用域、加入对象**时 `var_ref`；
- **弹栈、离开作用域、用完**时 `var_unref`；
- 引用计数归零 → 立即回收，无需等 GC。

回顾第 6 章的 `vm_push`/`vm_pop`：压栈 `var_ref`，弹出 `var_unref`，正是这套机制的体现。

### var_free：不是真的 free

`var_free` 并不马上把内存还给系统，而是清空内容后放进**空闲缓冲池**复用：

```c
void var_free(void* p) {
    var_t* var = (var_t*)p;
    uint32_t status = var->status;
    // 若是函数，先释放闭包引用
    var_clean(var);            // 清空 children、value 等
    var->type = V_UNDEF;
    if(status == V_ST_GC) {
        if(vm->gc.is_doing_gc) var->status = V_ST_GC_FREE;  // GC 中，延后处理
        else { remove_from_gc(var); add_to_free(var); }
    } else if(status != V_ST_FREE) {
        add_to_free(var);      // 放进空闲池
    }
}
```

`var_new` 会优先从空闲池取：

```c
inline var_t* var_new(vm_t* vm) {
    var_t* var = get_from_free(vm);       // 先复用空闲的
    if(var == NULL) var = mario_malloc(sizeof(var_t));  // 没有才新分配
    memset(var, 0, sizeof(var_t));
    var->type = V_UNDEF;
    var->status = V_ST_REF;
    hash_map_init(&var->children);
    return var;
}
```

**缓冲池的意义**：脚本执行会频繁创建/销毁临时值（每次运算都产生中间结果）。复用已分配的 `var_t` 内存块，能显著减少 `malloc`/`free` 调用，降低碎片——这对嵌入式尤其重要。池子的大小由 `free_var_buffer_num`（默认 `FREE_VAR_BUFFER_NUM_DEF = 128`）控制。

## 8.4 为什么还需要标记清除

引用计数有个致命弱点：**无法回收循环引用**。例如：

```javascript
var a = {};
var b = {};
a.ref = b;
b.ref = a;
a = null;
b = null;
```

此时 `a`、`b` 互相引用，各自的 `refs` 都不为 0，但它们已经不可达（垃圾）。这就是标记清除 GC 出场的地方。

### 触发时机（机会式、延迟到安全点）

当 GC 观察列表 `gc_vars` 的数量超过阈值时，并**不会就地立刻回收**，而是置一个 `gc_pending` 标志，延迟到下一个安全点再执行：

```c
static inline void add_to_gc(var_t* var) {
    vm_t* vm = var->vm;
    if(vm == NULL) return;              // 哨兵：回收堆内存而非活变量，直接返回
    // ... 用尾指针 gc_vars_tail 做 O(1) 追加到 gc_vars 链表 ...
    var->status = V_ST_GC;
    vm->gc.gc_vars_num++;

    /* 对象图正在被拆除（var_clean）时不触发 gc：重入的 gc_free_free_vars()
     * 会 mario_free() 掉同一拆除过程中尚未完成的 node_free() 仍要解引用的 var，
     * 造成 use-after-free。因此延迟到下一次不在拆除中的机会。 */
    if(vm->gc.gc_vars_num > vm->gc.gc_trig_var_num && vm->gc.gc_defer == 0)
        vm->gc.gc_pending = true; /* 在下一个 vm_run 安全点被消费 */
}
```

这个 `gc_pending` 标志在第 6 章讲过的 `vm_run` 主循环顶部被消费：**在两条指令之间**（此时值栈/作用域栈完整持有所有活变量，不存在 native C 帧裸引用的 var）才真正调 `gc(vm, false)`。这就是「机会式 GC 安全点」。

两个与安全性相关的字段：

- **`gc_defer`**：当对象图暂时未被 root 住时（`var_clean` 拆除、`func_call` 参数布置）>0，此时推迟机会式 GC，避免误扫。
- **`gc_pending`**：已请求但被推迟到下一个 `vm_run` 指令边界的 GC。

此外 `vm_pop_scope`（作用域弹出）后也会 `gc(vm, false)` 检查一次。

### 标记清除算法：gc_vars

```c
static inline void gc_vars(vm_t* vm) {
    // ① 从「根」出发，标记所有可达对象
    gc_mark(vm->root, true);        // 全局对象及其成员
    gc_mark_stack(vm, true);        // 操作数栈上的对象
    gc_mark_cache(vm, true);        // 缓存里的对象

    // ② 释放观察列表中「未被标记」的对象（不可达 = 垃圾）
    var_t* v = vm->gc.gc_vars;
    while(v != NULL) {
        var_t* next = v->next;
        if(v->status == V_ST_GC && v->gc_marked == false)
            var_free(v);
        v = next;
    }

    // ③ 清除标记，为下次 GC 做准备
    gc_mark(vm->root, false);
    gc_mark_stack(vm, false);
    gc_mark_cache(vm, false);

    // ④ 把 GC 期间标记为 GC_FREE 的对象移入空闲池复用
    ...
}
```

三个「根」：
1. **`vm->root`**：全局对象，所有全局变量/内建类都可达；
2. **操作数栈**：正在计算的中间值；
3. **缓存**：`var_cache` 里被运行时优化缓存的常量。

### 标记的递归与防环

`gc_mark` 递归遍历对象的 `children`：

```c
static inline void gc_mark(var_t* var, bool mark) {
    if(var_empty(var)) return;
    var->gc_marking = true;       // 标记「正在处理」，防止循环引用导致无限递归
    var->gc_marked = mark;
    hash_map_iterate(&var->children, gc_mark_callback, &mark);  // 递归标记所有成员
    var->gc_marking = false;
}
```

`gc_marking` 字段就是防环的关键：如果一个对象正在被标记，再次遇到它就跳过，避免 `a→b→a` 无限递归。

## 8.5 gc 总控

```c
static inline void gc(vm_t* vm, bool force) {
    if(vm->gc.is_doing_gc) return;                        // 防重入
    if(!force && vm->gc.gc_defer > 0) return;             // 有 C 帧正裸引用 var，推迟
    if(!force && vm->gc.gc_vars_num < vm->gc.gc_trig_var_num)
        return;                                            // 没到阈值，跳过
    vm->gc.is_doing_gc = true;
    gc_vars(vm);                                           // 标记清除
    gc_free_free_vars(vm, force ? 0 : vm->gc.free_var_buffer_num);  // 收缩空闲池
    vm->gc.is_doing_gc = false;

    /* 自适应触发：gc_vars_num 现在是存活计数。要求堆在它之上再增长 ~1.5x
     * 才做下一次机会式回收，这样构造一个全存活的大结构（大数组/对象字面量）
     * 是摊还 O(n)，而不是每超过固定下限就重标整个堆的 O(n^2)。 */
    uint32_t live = vm->gc.gc_vars_num;
    uint32_t trig = live + (live >> 1);
    vm->gc.gc_trig_var_num = (trig < GC_TRIG_VAR_NUM_DEF) ? GC_TRIG_VAR_NUM_DEF : trig;
}
```

- `force=false`：常规机会式回收，只在观察列表够大时进行，空闲池保留一定数量以备复用。
- `force=true`：彻底回收（如 VM 关闭时），空闲池清零，把内存全还给系统。

**自适应阈值是「gc speed up」的关键**：早期版本用固定阈值（`GC_TRIG_VAR_NUM_DEF = 128`），当脚本构造一个很大的、全部存活的对象（比如上千个成员的大对象）时，每新增一个变量都会触发一次全堆重标，总体退化为 O(n²)，会把引擎冻结数秒。现在回收后把下一次触发阈值提到「存活数 × 1.5」（并不低于固定下限 128），使大堆构造变为摊还 O(n)；而一次释放很多的回收又会把阈值缩回来，保证小堆仍能及时回收。

`gc_free_free_vars` 会在空闲池超过保留量时，把多余的空闲块真正 `mario_free` 掉。

## 8.6 混合策略为何适合嵌入式

| 机制 | 优点 | 在本项目中的作用 |
| --- | --- | --- |
| 引用计数 | 回收及时、无停顿峰值 | 绝大多数临时值一 unref 就回收 |
| 标记清除 | 能处理循环引用 | 兜底清理引用计数的盲区 |
| 空闲缓冲池 | 减少 malloc/free、降低碎片 | 频繁创建的临时 `var_t` 复用同一批内存 |
| 机会式安全点 | 回收只在所有活变量都被 root 住时发生 | 避免 native C 帧裸引用被误扫 |
| 自适应阈值 | GC 不会太频繁，也不会退化为 O(n²) | 触发阈值随存活数×1.5 动态上移（不低于 128） |

这套组合让 Mario 在没有大内存、没有操作系统内存管理支持的单片机上也能稳定运行脚本。

## 8.7 小结

- 内存分配抽象为 `_platform_malloc/free`，方便移植。
- `var_t` 用引用计数管理，`refs` 归零即回收。
- 回收不是真 `free`，而是清空后进**空闲池**复用。
- 循环引用由**标记清除 GC**兜底：从 root/栈/缓存三个根标记可达对象，清除不可达者。
- GC 是**机会式**的：`add_to_gc` 只置 `gc_pending`，真正的回收延迟到 `vm_run` 指令边界的安全点。
- **自适应触发阈值**（存活数×1.5）把大堆构造从 O(n²) 降为摊还 O(n)，这是「gc speed up」的核心。
- `gc_marking` 防止标记阶段无限递归。
